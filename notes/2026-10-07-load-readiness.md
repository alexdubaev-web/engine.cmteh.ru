# Аудит готовности к нагрузке

Дата: 2026-10-07. Исследованный коммит: `9a3bc1ae13a38db5f3fa85427270e3b9ce90dbae`. Статус: аудит и предложения, изменения backend и нагрузочные испытания не выполнялись. Точные значения пропускной способности не установлены.

## Текущая архитектура

- Production уже выбран и работает на REG.RU: статические HTML/изображения/JS/CSS, PHP API, MySQL, SMTP и два задания cron. Новое облако не является обязательным условием тестирования.
- Поиск/фильтрация каталога выполняются в браузере. Просмотр товара не читает БД. Но `public/assets/app.js:49-50` при каждой загрузке страницы вызывает динамический GET `/api/config.php`, даже если посетитель не отправляет заявку. Перед отправкой формы выполняется ещё один GET config, затем POST `/api/orders.php`.
- `src/worker-runtime.mjs:3-4` и Node preview возвращают отключённый демонстрационный API. Развёртывание только `npm start` не воспроизводит production backend.
- GET config создаёт `Orders`, открывает PDO, читает каталог, выполняет `listing()` и создаёт сессионный CSRF. POST проверяет Origin, CSRF, лимиты тела/полей, цены из серверного каталога, шифрует данные, записывает заявку и при включённой immediate_delivery пытается отправить письмо.
- Заявки, очередь отправки и доказательство согласия находятся в одной таблице orders. Redis, отдельной очереди, S3 и постоянно работающего worker сейчас нет. Резервная обработка почты - конечный CLI batch, не демон.

## Проверено на рабочем сервере только чтением

PHP CLI 8.3.31, PDO mysql/sqlite, sodium. Активная конфигурация: MySQL; enabled=true; immediate_delivery=true; rate_limit=8 успешных заявок на IP за 900 секунд; retention_days=90. CLI сообщает session.save_handler=files и gc_maxlifetime=1440. Веб-код не задаёт другой handler; отдельный web-SAPI override ещё необходимо проверить, не выдавая phpinfo публично.

Crontab этого приложения: `*/5 * * * * mail:retry` и `17 3 * * * purge`. Часовой пояс самого cron не проверен. Секреты, DSN, SMTP credentials, тела заявок и CSRF не сохранялись.

MySQL: 5.7.44-48, InnoDB, READ-COMMITTED, innodb_flush_log_at_trx_commit=0, max_connections=2000. Последние два значения принадлежат общему серверу хостинга, не являются персональной квотой приложения или доказательством его мощности. Настройки PHP-FPM/Apache, выделенные CPU/RAM, IOPS и лимиты аккаунта неизвестны.

information_schema показывает приблизительно две строки orders, не точный COUNT. В orders существуют только PRIMARY(id) и UNIQUE(order_number); в rate_limits только PRIMARY(bucket). EXPLAIN действующих запросов listing и due-mail показывает ALL / Using filesort, у due-mail также Using where. При двух строках это само по себе ещё не проблема скорости, но отсутствие индексов подтверждено и станет существенно при росте таблицы.

## Ограничения и предложения

1. **SMTP в HTTP-пути.** `backend/api/orders.php:20`, `backend/app.php:145-165`: после commit POST вызывает deliver(1), который может отправлять старейшую чужую заявку. Сетевой SMTP занимает PHP worker; даже повторная идемпотентная отправка может запускать mail scan. Нужно быстро отвечать после записи и обрабатывать durable outbox отдельно. Выключить immediate_delivery без замены worker недостаточно: стандартный cron выбирает максимум 20 кандидатов за пять минут, то есть максимум 0,067 кандидата/сек при одном неперекрывающемся запуске, а успешных отправок может быть меньше.
2. **Последовательный счётчик номера.** `backend/app.php:73-81,132-134`: SELECT FOR UPDATE одной строки сериализует все новые заявки; блокировка удерживается до шифрования, INSERT и commit. При цели 5000 новых заявок/сек средний участок владения этой блокировкой должен быть менее 0,2 мс. Это требование к расчёту, не измерение времени. Нужен согласованный контракт нумерации: уникальные возрастающие номера с допустимыми пропусками позволяют AUTO_INCREMENT/sequence; требование непрерывных номеров сохраняет общий барьер. Для преимущественно чтения этот пункт может быть необязательным.
3. **Тяжёлый config и отсутствие индексов.** `backend/api/config.php:6`, `backend/app.php:146,177-181`: выдача CSRF сортирует до 100 заявок как проверку схемы. Заменить на дешёвую проверку готовности без чтения списка, добавить индекс времени создания, времени очистки rate_limits и подобрать составной индекс outbox по EXPLAIN на реалистичных данных. Результат config с персональным токеном нельзя кешировать целиком в CDN. Индексы выбирать с учётом цены записи, а не добавлять все сочетания.
4. **Файловые сессии и proxy IP при горизонтальном масштабировании.** `backend/api/common.php:12-16`, `backend/api/orders.php:9-11,18`: локальные файлы не обеспечивают общий CSRF между узлами и после замены контейнера. Нужен общий session store или отдельно спроектированный подписанный CSRF-протокол. Sticky sessions не решают потерю узла. Client IP нужно восстанавливать только из доверенной цепочки proxy; произвольный X-Forwarded-For принимать нельзя. Это условия новой инфраструктуры, а не доказанный баг текущего одиночного хостинга.
5. **Лимит IP и честная модель нагрузки.** `backend/app.php:126-130`: один генератор с одним IP быстро получит 429. Нельзя считать 5000 отклонённых запросов/сек успешной работой с БД. Проверять защиту отдельным production-подобным сценарием; для записи использовать согласованный, защищённый профиль тестового контура либо реалистичные источники. Не менять лимит production и не подделывать клиентский IP через недоверенный заголовок.
6. **Неверная классификация ошибок БД.** Подтверждённая ошибка SQLSTATE -> 409 описана в [отдельной заметке](2026-10-07-order-integrity-error.md). Исправить перед испытаниями; временные ошибки блокировок и подтверждение commit измерять отдельно, повторы ограничивать и выполнять с тем же UUID.
7. **Сохранность commit.** Значение flush=0 означает, что подтверждённый commit может быть потерян при аварии. Подробности в [заметке о сохранности](2026-10-07-db-durability.md). Производительность нельзя сравнивать, меняя этот контракт незаметно.
8. **Объём payload.** `backend/app.php:131-134`: полный HTML согласия входит в каждую зашифрованную запись. В опубликованном архиве документ занимает 24 489 байт; одна его base64-составляющая даёт не менее 32 652 байт на заявку. При 5000 новых заявок/сек это около 163 МБ/сек и 98 ГБ за десять минут только для этой части, без остальных полей, индексов, redo/binlog, реплик и backup. Для высокого потока записей нужен неизменяемый версионированный документ в отдельном хранилище с hash/ref и обратной совместимостью экспорта. Не удалять доказательство согласия ради скорости. При редких заявках оптимизацию можно отложить.
9. **Диагностика и тесты.** `backend/api/config.php:11`, `orders.php:24`, `app.php:151`: exceptions скрываются без внутренней категории, поэтому 503/retry не объясняются логами приложения. Нужны correlation ID, категории ошибок без PII/секретов и метрики latency, DB, очереди. Основные проверки используют SQLite; eight-process test не доказывает MySQL capacity. `tests/backend.php` имеет CM_TEST_DSN, но ниже содержит SQLite-only CREATE TRIGGER / RAISE, поэтому весь suite нельзя просто переключить на MySQL без исправления.

## Неизвестное и следующий этап

Локальные функциональные проверки выполнены с процессным включением имеющихся SQLite/sodium расширений: `tests/backend.php` - 30 PASS, `tests/backend-export.php` - 3 PASS. Тест false-409 закрепляет обнаруженный баг и потому его PASS не означает исправление. MySQL concurrency и нагрузка не запускались; pcntl на Windows отсутствует.

Ждём определения RPS mix, бюджетов, географии и решения сохранить REG.RU или мигрировать. Для оставленного REG.RU нужен действительно отдельный аккаунт/контур с подтверждённой изоляцией ресурсов и разрешённой провайдером нагрузкой. Второй домен на том же аккаунте с общей БД/worker pool не является изолированным стендом.

Окончательный план нагрузочного теста будет написан после первоочередных правок и smoke-проверки стенда. Открытые заметки позже преобразуем в `tasks/<task.md>` после согласования приоритетов; сейчас задачи исполнения не созданы.
