# Production: минимальный старт и постепенный рост

Статус: предварительные правила; финальные sizes/tier, RPS capacity и runbook будут заполнены после нагрузочного теста. Не является утверждённым provisioning plan.

1. Сохранить статический каталог: чтение товаров/поиск не переносить в БД без необходимости. Считать отдельно загрузку assets, config и POST. Около 2 RPS сайта не требует автоматически базы под 5000 записей/сек.
2. Начать с одного небольшого API узла и минимального подходящего MySQL tier/действующего тарифа, если допустим downtime узла. Малый flow может обслуживаться отдельным scheduled outbox job; если нужно быстрое письмо и предсказуемое восстановление очереди, один небольшой worker. Для горизонтального роста сессии и proxy контракт должны быть решены заранее.
3. Если требуется доступность при отказе, минимум определяет SLA: два API узла, резервирование DB и session store могут быть нужны уже при 2 RPS. Один DB узел дешевле, но не становится HA от слова managed. Выбор доступности независим от RPS.
4. На стенде измерить одного API узла при разных PHP process limits. В качестве начального правила планирования брать 60-70% измеренной устойчивой ёмкости, проверив p95/p99 и recovery; это предлагаемая политика запаса, не уже полученная capacity.
5. Масштабировать API горизонтально при росте p95/p99, очереди PHP, CPU и исчерпании headroom. Ограничить max replicas так, чтобы совокупные DB connections и session store выдерживали масштабирование. Автомасштабирование не исправляет общий counter-row lock.
6. Увеличивать DB tier вертикально после оптимизации SQL/индексов, если метрики показывают устойчивое ограничение CPU, working set/RAM, disk latency/IOPS или connections. Больше RAM не устраняет lock contention. Read replicas не масштабируют текущую запись orders.
7. Масштабировать worker независимо, по возрасту/размеру outbox и возможностям SMTP. Если SMTP drain rate меньше поступления, любой быстрый HTTP tier только увеличивает backlog; нужен договорённый режим доставки/агрегации либо предел новых заявок.
8. Постоянно отслеживать размер DB/backup, queue age, errors, budget. Alert thresholds подобрать из исходной измеренной нормы; предлагаемые предварительные сигналы - p95 выходит за SLA, DB/API CPU >70% несколько минут, disk >70%, queue age выше утверждённого срока. Проверить эффективность выбранного autoscaler и время scale-up отдельно.
9. Для каждого vertical DB upgrade: backup/restore rehearsal, окно изменения, подтверждённый downtime/failover, compatible driver/DDL/flush, повтор representative test. У DO Standard учитывать объявленные ограничения новых tiers; переход в другую edition может потребовать отдельной миграции.
10. После каждого release небольшой smoke/regression тест; большая нагрузка только в изолированном контуре. Артефакты: image/commit, tier, конфиги, dataset, seed, сценарии/результаты k6, обезличенные логи, стоимость, fixes и остаточные ограничения. Новые дефекты записывать в notes и позднее превращать в tasks, не терять первичные доказательства.

Генератор: предварительный кандидат отдельная Linux VM 4-8 vCPU, 8-16 GiB RAM и проверенная сеть; это ещё не утверждённый размер. Ёмкость подтвердить калибровкой, CPU/RAM/network/FD и dropped_iterations. При 10000 RPS и среднем ответе 100 KB только payload требует около 1 GB/s, поэтому один небольшой сетевой интерфейс может стать ограничением; выбирать размер по конкретному mix, а не по числу RPS. [k6: большой тест и генератор](https://grafana.com/docs/k6/latest/testing-guides/running-large-tests/).
