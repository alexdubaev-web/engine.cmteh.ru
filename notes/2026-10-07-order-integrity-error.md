# Неверный HTTP 409 для посторонней ошибки целостности БД

Статус: подтверждено чтением кода и независимым ревью; runtime-воспроизведение на MySQL ещё не выполнено. Приоритет P2. Код не менялся.

## Проблема

`backend/app.php:135-141` обрабатывает любой PDO SQLSTATE 23000/23505 как столкновение requestId. Если строка с этим UUID отсутствует, возвращается ApiError 409 «Этот номер уже использован другой заявкой».

SQLSTATE 23000 в MySQL охватывает ошибки целостности, не только дубликат PRIMARY(id). Например, счётчик last_number может оказаться ниже уже существующего order_number; следующий INSERT нарушит UNIQUE(order_number), хотя requestId новый. Транзакция откатится, UUID не сохранится, пользователь получит ложный конфликт; повтор не устранит неисправность.

`tests/backend.php` в конце создаёт SQLite trigger reject_order с RAISE(ABORT), а затем ожидает 409. Такая проверка закрепляет неправильное поведение и одновременно делает эту часть suite несовместимой с MySQL.

## Предлагаемое исправление

Разрешать успешный idempotent replay только при существующей строке с тем же UUID и тем же intent. Конфликт содержимого возвращать 409 только при существующей строке с этим UUID и отличающимся intent. Остальные ошибки целостности классифицировать внутри приложения и возвращать безопасную серверную ошибку; не переименовывать их в пользовательский конфликт. Сверять errorInfo и ограничения конкретного драйвера без зависимости исключительно от текста ошибки.

## Условия приёмки

- Одинаковые параллельные UUID/intent создают одну строку и возвращают один номер.
- Одинаковый UUID с другим intent возвращает 409 и не меняет запись.
- Дубликат order_number при новом UUID не возвращает ложный 409; транзакция полностью откатывается и причина отражается в обезличенном внутреннем логе.
- Не связанное с requestId ограничение/trigger failure не маскируется.
- Проверки выполняются в изолированных MySQL и SQLite, без production DSN.

В этой исследовательской сессии reviewer смог выполнить backend-export.php; backend.php не запустился из-за отсутствия подключённого PDO driver в локальном CLI, concurrency suite пропущен без pcntl. Это не новый регрессионный результат и не нагрузочный тест.

Lead затем включил уже установленный pdo_sqlite и sodium только для отдельного CLI процесса (`php -n -d extension_dir=... -d extension=php_pdo_sqlite.dll -d extension=php_sodium.dll tests/backend.php`). Все 30 PASS прошли, включая существующий trigger-abort -> 409. Таким образом, неверная классификация реально воспроизведена на изолированном SQLite, а описанный MySQL duplicate-order-number случай всё ещё требует отдельной регрессии. backend-export.php также прошёл, 3 PASS. Настройки PHP и production не изменялись.
