# Независимое код-ревью сайта — 7 октября 2026

Проверено текущее состояние `setup/engine-regru`, HEAD `e71f1541acec77b3d5f671bea5313f971b7594f5`, включая незакоммиченные изменения и новые файлы. Ревью относится ко всему сайту, поэтому включает существовавшие до текущих изменений ошибки. Исходники сайта не исправлялись. Добавлены только этот отчёт, диагностические сценарии и логи в его каталоге.

Выявлено 10 воспроизводимых проблем уровня P2: ошибки в обычных сценариях или при конкретном сбое, требующие исправления. P0/P1 в проверенном объёме не выявлены. Основные пользовательские риски: продолжение аналитики после отказа в другой вкладке, потеря изменений корзины и нарушение идемпотентности повторной заявки.

**Объём и ограничения проверки**

Независимые агенты проверили PHP-приём заявок, очередь писем и CLI, браузерные модули, сборку, упаковку, маршрутизацию, импорт каталога/остатков/изображений и настройку хостинга. Ведущий проверил соответствующие участки кода и повторил диагностические сценарии. Проверены существующие тесты, свежие сборки обоих режимов, синтаксис PHP/JS/Python и HTTP-обработка PHP API с тестовой SQLite.

Сборки и ошибки воспроизводились в отдельной временной копии. Реальные `backend/config.php`, пароли и ключи не читались. Реальные заявки, SMTP и IndexNow не отправлялись. Продакшен-хостинг, Apache, настоящая MySQL и реальные браузеры не запускались; их поведение нельзя считать проверенным этими тестами. Два сценария корзины используют модель конкретных операций из `app.js`, а не полный DOM-тест. Сценарий аналитики исполняет настоящий модуль в двух VM-контекстах; импорт и IndexNow исполняют настоящие скрипты с подменой сети/ошибки записи.

   Исправление: подписать каждый контроллер на изменение ключа согласия; при отказе или удалении записи остановить локальный счётчик. Не записывать ответное событие без необходимости. Регрессионный тест: две вкладки с общим хранилищем, первая уже инициализирована, отказ во второй приводит к `destruct` в первой.

Затем обработчик `storage` присваивает устаревшее `event.newValue` и вызывает `saveCart()`, снова записывая его в общее хранилище. При встречных отложенных событиях вкладки непрерывно переписывают старые значения. В модели с подавлением записей одинакового значения обработано 100 событий, ещё 2 остались в очереди; один из двух товаров потерян. Ошибка существовала в HEAD.

   Исправление: отделить отрисовку от записи, не писать в localStorage из обработчика уведомления. Для конкурентных изменений определить стратегию: сериализованные операции, журнал операций/ревизии с разрешением конфликтов либо транзакционная модель хранения. Простое перечитывание перед записью само по себе не устраняет гонку. Регрессионный тест: два независимых добавления и реалистичная очередь `storage`, оба товара сохраняются, очередь событий завершается.

**TDD и недостающие тесты**

Под TDD здесь оценивались тесты и возможность проверить подход «сначала тест». История содержит один исходный коммит и незакоммиченные изменения: она не позволяет установить порядок написания кода и тестов. Поэтому утверждать, что TDD соблюдён или нарушен, нельзя. Проходящий тестовый набор не доказывает отсутствия гонок.

Имеющиеся проверки полезны: backend проверяет шифрование, валидацию, серверные цены, согласие, последовательную идемпотентность, rate limit и повтор доставки; аналитика — ошибки localStorage и устаревшие callbacks; HTML — ссылки, метаданные и schema; импорт остатков — сопоставление артикулов. При этом `app.js` не исполняется существующими тестами вообще.

В первую очередь нужны RED→GREEN регрессионные тесты для пунктов 1–6, затем отказоустойчивость сборки/упаковки и импортов. Нужны реальные браузерные проверки форм и двух вкладок, HTTP-тесты fail-closed отключения API, интеграционные тесты конкурентных `accept`/`deliver` на MySQL, проверка Apache canonical redirects/404/security headers и Linux-тесты provisioning с правами/симлинками/конкурентным запуском. Их отсутствие отмечается как предел аудита; соответствующие механизмы не объявляются сломанными без доказательства.

Диагностические скрипты в этом каталоге подтверждают существующие ошибки; их `PASS` означает успешное воспроизведение дефекта. Это не добавленные регрессионные тесты ожидаемого исправленного поведения и не свидетельство TDD.

**Наблюдения, не включённые в 10 основных дефектов**

- [console.php:22](../../../backend/console.php#L22) не проверяет полный результат `fwrite` и `fclose`, после чего сообщает об успешном экспорте. На короткой/ошибочной записи сообщение будет ложным. Подтверждено чтением кода, ошибка диска не воспроизводилась; добавить проверку полного количества байтов и отказ с удалением неполного файла.
- [import_catalog.py:4](../../../import_catalog.py#L4) привязан к пути `/tmp/codex-remote-attachments/...` и пишет products.json при исполнении/импорте модуля. Его нельзя считать переносимой утилитой повторного импорта; нужен аргумент пути и main guard. Этот импорт не запускался на реальном workbook.
- Rate limit использует фиксированные 15-минутные окна, поэтому допускает двойной burst на границе окна. Требование скользящего окна не задано; это поведение политики, не подтверждённый блокирующий дефект.
- `deliver()` атомарно захватывает lease условным UPDATE и завершает отправку с проверкой lease-токена. Гонка обычного одновременного захвата по коду не обнаружена. Повтор письма после принятия SMTP и падения процесса остаётся свойством доставки как минимум один раз; Message-ID не доказывает дедупликацию получателем.
- Неэкранированный SKU в части шаблонов требует улучшения, но заявленная возможность XSS через один только импорт workbook не подтверждена: неизвестный SKU останавливает сборку на `COPY[p['sku']]`. Это не оформлено как эксплуатируемая уязвимость сайта.

Для PHP может потребоваться явно указать `-d extension_dir=ПУТЬ_К_PHP/ext`; глобальный php.ini не изменялся. Python-сценарий использует временные fixtures и подменяет сеть. PHP-сценарий изменяет только временную копию каталога. Скрипты не отправляют реальные заявки. Проверки сборки/упаковки с намеренными ошибками запускать только в отдельной копии: сами найденные дефекты делают такие команды разрушительными для существующих артефактов.
