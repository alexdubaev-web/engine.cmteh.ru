# Измерение обращений и пути покупателя

Счётчик: **113475902**, engine.cmteh.ru. Подготовлено 3 ноября 2026 года
по поручению владельца «настрой все важные метрики».

## Основная и вспомогательные цели

| Роль | Название | Тип / идентификатор | Что означает |
| --- | --- | --- | --- |
| Основная, избранная | Заявка принята сервером | JavaScript / `form_success` | Клиент получил корректную квитанцию backend для отправленного requestId; одна обработка подтверждения |
| Вспомогательная | Поиск по каталогу | JavaScript / `search` | Поиск после паузы ввода; передаются длина запроса и число результатов, без текста запроса |
| Диагностическая | Поиск без результатов | JavaScript / `search_empty` | Нулевая выдача поиска; не положительная конверсия |
| Вспомогательная | Товар добавлен в корзину | JavaScript / `add_to_cart` | Завершена операция изменения корзины; параметры SKU и количество |
| Вспомогательная | Открытие корзины | JavaScript / `cart_open` | Пользователь открыл корзину |
| Вспомогательная | Начало заполнения заявки | JavaScript / `form_start` | Первое изменение/попытка отправки формы; `kind=inquiry` либо `cart` |
| Диагностическая | Ошибка заявки | JavaScript / `form_error` | Ошибка проверки полей, отказ backend или неопределённый сетевой результат; без контактных данных |
| Контактная | Клик по номеру телефона | Встроенная `phone` | Клик по одному из четырёх опубликованных tel:; не состоявшийся звонок |
| Контактная | Клик по email | Встроенная `email` | Клик по одному из двух опубликованных mailto:; не отправленное письмо |

JavaScript-цели используют точное совпадение идентификатора. Для phone/email
условия берутся из актуальных публичных контактов. Скрытие телефонных номеров
не включается. Существующая автоцель формы сохраняется как отдельное измерение;
её результаты нельзя складывать с `form_success` как разные заявки.
Диагностические и промежуточные события не выбираются как продажи или цели
автоматической оптимизации рекламы.

## Что уже работает в коде

`public/assets/app.js` формирует семь событий, `public/assets/analytics.js`
передаёт разрешённые события через `reachGoal` после согласия и загрузки счётчика.
В этой задаче код сайта не меняется. Контакты отслеживаются встроенными целями.

`form_success` требует HTTP-успеха, `ok === true`, совпадения валидного UUID
с отправленным requestId, корректной даты и допустимого номера заявки.
Повторная обработка того же подтверждения не создаёт второй success.
Ошибка, таймаут или скачивание списка без отправки не считаются успехом.
Событие подтверждает регистрацию, а не доставку письма, оплату или продажу.

Передаваемые параметры ограничены whitelist; имя покупателя, телефон, email,
комментарий, CSRF и requestId в аналитические параметры не добавляются.
До согласия, после отказа и при недоступном счётчике аналитических событий может
не быть, даже если backend принял заявку. Согласие и фильтры счётчика не меняются.

## Настройка через API

Секрет берётся только из `YANDEX_OAUTH_TOKEN`. Нужен OAuth владельца с правом
изменять Метрику (`metrika:write`; для чтения также `metrika:read`). Владение
счётчиком в ответе API само по себе не доказывает наличие write-scope у токена.

План без записи в Яндекс:

```powershell
pwsh -File tools/configure_metrika_goals.ps1 -EvidenceDir C:/path/to/new-evidence-directory
```

Создание отсутствующих целей после предоставления write-доступа:

```powershell
pwsh -File tools/configure_metrika_goals.ps1 -EvidenceDir C:/path/to/another-new-evidence-directory -Apply
```

Используйте отдельную папку свидетельств каждого запуска. Скрипт проверяет
счётчик и домен, сопоставляет существующие цели по типу и условиям, не создаёт
повторные совпадающие цели, сохраняет состояние до/после и проверяет результат
отдельным GET. Старые цели не удаляются и не переписываются. Автоматических
повторов POST нет. После неопределённого исхода сначала требуется GET-сверка.
API фактически требует числовые 0/1 в `is_favorite`, несмотря на boolean
в сгенерированной схеме документации; корректный формат подтверждён отсутствием
ошибки парсинга после исправления.

## Как читать результат

Посещения, пользователи, просмотры, источники, поисковые системы, устройства,
посадочные и UTM уже доступны стандартными отчётами. Их сопоставляют с основной
целью за одинаковые полные периоды. Просмотры и время не подменяют обращениями.

Для корзины смотрят путь `add_to_cart → cart_open → form_start → form_success`.
Прямые обращения через подбор товара анализируют отдельно по `kind=inquiry`:
они могут обходить корзину. Ошибки и пустой поиск показывают места потери спроса.
Телефон/email рассматривают отдельно от принятых форм; без коллтрекинга нельзя
получить число состоявшихся звонков или их результат.

При оценке заявок проверяют агрегированные регистрации backend за тот же период.
Для подсчёта оплаченных заказов и выручки нужна отдельная интеграция с учётной
системой; цены корзины и факт регистрации не объявляются выручкой.
Включённая в теге настройка `ecommerce` сама по себе не означает передачу purchase.
Исторические достижения новых целей задним числом не обещаются.
